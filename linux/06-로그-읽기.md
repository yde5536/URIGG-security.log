# 리눅스 제로부터 #6 - 로그 읽기

> 📝 블로그 원문: [[리눅스 제로부터 #6 - 로그 읽기]](https://urigg-security.tistory.com/entry/%EB%A6%AC%EB%88%85%EC%8A%A4-%EC%A0%9C%EB%A1%9C%EB%B6%80%ED%84%B0-6-%EB%A1%9C%EA%B7%B8-%EC%9D%BD%EA%B8%B0)

이전 편에선 `grep`과 `|`로 파일 안에서 원하는 부분만 찾고, 명령어끼리 연결해 실행시키는 방법을 공부했다. 이 도구들을 실제 로그에 써 보기 전에, 이번 편에선 먼저 로그가 무엇이고 어떻게 읽는지부터 알아보겠다.

## 로그란 무엇인가?

로그란 **컴퓨터가 "무슨 일이 있었는지" 스스로 적어두는 기록 파일**이다. 아래 예시를 통해 더 알아보겠다.

```
Sep 28 07:42:11 ubuntu sshd[1234]: Failed password for urigg from 192.168.0.50 port 54321 ssh2
```

9월 28일 7시 42분 11초에, `ubuntu`라는 컴퓨터에서 원격 접속 프로그램이 기록한 내용이다. **"누군가 `urigg` 계정으로 `192.168.0.50`에서 접속을 시도했지만, 비밀번호가 틀렸다."** 라는 기록이다. 이런 줄이 한 줄에 사건 하나씩, 일어난 순서대로 차곡차곡 파일에 쌓인다. 이 파일을 로그라고 부른다. 텍스트 파일로 남는 CCTV 같은 것이라고 이해하면 쉽다.

### 누가 적는 것인가?

로그는 프로그램들이 각자 적는다. 하나의 기록 담당자가 있는 게 아니라, 프로그램마다 자기가 한 일을 적는다. 예를 들어 원격 접속 프로그램(`sshd`)은 "누가 접속을 시도했고, 성공했는가 실패했는가"를 작성한다. 또 `sudo`는 "누가 관리자 권한으로 무슨 명령을 실행했나"를 작성한다.

## 보안에서 로그가 중요한 이유

### 침입은 실시간으로 잡히지 않는다

영화나 드라마 같은 매체에선 해킹을 당하는 순간 화면에 경고가 뜨고 사이렌이 울리는 장면이 자주 나온다. 그러나 현실은 다르다. 서버가 뚫리고 몇 주가 지나서야 알아채는 경우가 흔하다. 침입자는 들키지 않기 위해 최대한 조용히 숨어 있기 때문이다. 그래서 **이미 지나간 몇 주 동안 무슨 일이 있었는지**를 알려주는 것이 로그이다.

### 공격은 흔적이 튄다

사람은 비밀번호를 세 번쯤 틀리면 비밀번호 찾기를 하거나 포기한다. 그런데 공격자는 프로그램을 통해 **초당 수십 번씩 몇 시간을 시도한다.** 그 결과가 로그에 남는 것이다. 이게 로그 분석의 핵심이다.

```
Sep 28 03:12:01 ubuntu sshd[2001]: Failed password for root from 203.0.113.9 ...
Sep 28 03:12:02 ubuntu sshd[2002]: Failed password for admin from 203.0.113.9 ...
Sep 28 03:12:03 ubuntu sshd[2003]: Failed password for test from 203.0.113.9 ...
Sep 28 03:12:04 ubuntu sshd[2004]: Failed password for user from 203.0.113.9 ...
...
```

1초에 한 줄씩, 계정 이름을 바꿔가며 시도하는 것은 도저히 사람이라고 볼 수 없다. 이건 기계가 한 것이다. 그래서 로그만 봐도 **"이건 실수가 아니라 공격이다"** 를 구분할 수 있다.

### 공격자는 로그를 지운다

침입에 성공한 공격자가 가장 먼저 하는 일 중 하나는 로그 삭제 또는 조작이다. 자신의 흔적을 없애야 하기 때문이다. 이에 대비해 실무에서는 로그를 다른 서버로 실시간 전송해 따로 보관하거나, 로그 파일의 쓰기 권한을 최소화한다. 또한 누가 로그를 건드렸는지까지 로그로 남긴다. 역설적이지만 이는 로그가 그만큼 강력한 증거라는 뜻이기도 하다.

### 사고 대응과 법적 증거가 된다

실제 해킹 사고가 나면 언제, 어디서, 어떤 경로로 들어왔는지를 밝혀야 한다. 이걸 전문 용어로 **포렌식**이라고 한다.

**피해 범위**를 알아야 어떤 데이터가 털렸는지 안내할 수 있고, **침입 경로**를 알아야 같은 방법으로 또 뚫리는 걸 막을 수 있고, **기록**이 있어야 법적 증거가 된다.

## /var/log 들여다보기

1편 파일 구조를 공부할 때 루트(`/`) 밑에 `/home`, `/etc`, `/var` 같은 폴더들이 있고, 각자 하는 역할이 정해져 있다고 공부했다. `/var`는 **variable(변하는)** 의 약자이다. 내용이 계속 바뀌고 쌓이는 데이터가 들어가는 곳이다. 그중 로그만 모아둔 폴더가 `/var/log`이다.

```
cd /var/log
ls -l
```

위 명령어로 `/var/log` 폴더에 들어가서 파일을 확인해보면 파일이 쏟아져 나오는 것을 볼 수 있다.

### 자주 보게 될 로그 파일

실제로 자주 들여다보는 로그 파일들은 아래와 같다.

- `auth.log` : 로그인, `sudo` 사용 등 인증 관련 기록
- `syslog` : 시스템 전반의 잡다한 기록 (거의 모든 게 들어옴)
- `kern.log` : 커널이 남긴 기록 (하드웨어, 드라이버 문제 등)
- `dpkg.log` : 프로그램 설치/삭제 기록
- `apt/` : `apt` 명령 사용 기록 (파일이 아닌 폴더)

이번 편에선 `auth.log` 하나만 보겠다.

#### auth.log.1, auth.log.2.gz는 무엇인가?

목록을 보면 아래와 같은 것들이 같이 보인다.

```
auth.log
auth.log.1
auth.log.2.gz
auth.log.3.gz
```

로그는 **쌓이기만 하고 줄어들지 않는다.** 그냥 두면 몇 달 뒤에 수 기가바이트가 되고, 최악의 경우 디스크가 꽉 차서 서버가 멈춘다. 실제로 일어나는 사고다. 그래서 리눅스는 주기적으로 **로그 로테이션**을 한다.

```
지금 쓰는 파일 → .1 로 밀어냄 → .2.gz 로 압축 → 오래되면 삭제
```

그래서 파일 이름이 이런 뜻이 된다.

- `auth.log` : 지금 이 순간 기록이 쌓이고 있는 파일
- `auth.log.1` : 바로 지난 기간 기록
- `auth.log.2.gz` : 그 이전 기록이 압축된 것

### auth.log는 왜 잠겨 있을까? (권한 복습)

`ls -l`에서 `auth.log` 줄을 찾아 분석해 보겠다.

```
-rw-r----- 1 syslog adm 15095 Sep 28 08:10 auth.log
```

우선 권한 부분을 2편에서 배운 대로 잘라보겠다.

```
-    rw-    r--    ---
①     ②      ③      ④
```

- ①`-` : 일반 파일
- ②`rw-` : 주인은 읽기/쓰기 가능
- ③`r--` : 그룹은 읽기만 가능
- ④`---` : 나머지는 아무 권한 없음

그다음 부분은 **주인**과 **그룹**이다.

```
-rw-r----- 1 syslog adm
              ↑      ↑
             주인   그룹
```

주인인 `syslog`는 로그를 실제로 기록하는 프로그램이 쓰는 계정이다. 사람이 아닌 프로그램 전용 계정이다. 그 뒤 그룹 `adm`은 전통적으로 "로그를 봐도 되는 사람들" 그룹이다.

#### 로그에는 민감한 정보가 들어간다

**누가, 몇 시에, 어느 IP에서 접속했는지를** 통해 사람의 생활 패턴을 알 수 있다. 또 **아이디 칸에 실수로 비밀번호를 입력한 흔적**이나 **어떤 계정이 존재하는지**를 알 수 있다.

#### 왜 주인이 root가 아니라 syslog일까?

로그를 쓰는 프로그램에게 필요한 권한은 **로그 파일에 글을 쓰는 것** 하나이다. 그런데 그 프로그램을 `root`로 돌리면, 만약 그 프로그램에 취약점이 있을 때 공격자가 시스템 전체를 장악하게 된다.

그래서 로그 쓰기만 할 수 있는 전용 계정인 `syslog`를 따로 만들어서 돌린다. 이것을 **"최소 권한 원칙"** 이라고 한다.

#### 그런데 나는 왜 읽을 수 있는가?

나는 이 파일을 `sudo` 없이 읽을 수 있다. `adm` 그룹에 속해 있기 때문이다.

```
groups
```

위 명령어를 입력해 출력된 결과에 `adm`이 보이면 된다. 우분투는 설치할 때 만든 첫 번째 사용자를 자동으로 `adm` 그룹에 넣어준다.

## auth.log 한 줄 읽기

4편에서 배운 `less`로 로그를 열어보겠다.

```
less /var/log/auth.log
```

처음 보면 알아보기 힘들지만 구조는 모든 줄이 같다.

```
Sep 28 07:42:11 ubuntu sshd[1234]: Failed password for urigg from 192.168.0.50 port 54321 ssh2
```

위 한 줄을 잘라보면 아래와 같다.

```
Sep 28 07:42:11    ubuntu    sshd[1234]:    Failed password for urigg from 192.168.0.50 port 54321 ssh2
       ①             ②           ③                      ④
```

- ①시각 : 언제 일어났는지
- ②호스트명 : 어느 컴퓨터에서
- ③기록한 프로그램[번호] : 어떤 프로그램이 이 줄을 기록했는가
- ④실제 내용 : 무슨 일이 있었는가

### ③의 대괄호 속 숫자는 무엇인가?

```
sshd[1234]
     ↑
```

이 숫자는 **PID(프로세스 번호)** 이다. 실행 중인 프로그램마다 컴퓨터가 붙여주는 번호다. 같은 프로그램이라도 실행될 때마다 번호가 달라진다. 그래서 **"이 줄과 저 줄이 같은 접속 시도에서 나온 건지"** 를 구분할 때 쓴다. 번호가 같으면 같은 프로세스가 남긴 기록이다.

### sshd가 무엇인가?

`sshd`는 원격 접속을 받아주는 프로그램이다. 1편에서 "서버는 화면 없이 멀리서 원격으로 조작한다" 라는 것을 배웠다. 그때 쓰는 게 SSH이고, 서버 쪽에서 그 접속을 받는 프로그램이 `sshd`이다. 간단히 말해 **인터넷 너머에서 들어오는 접속을 처리하는 프로그램**이다. 인터넷에 열려 있는 문이기 때문에, 공격자가 가장 먼저 두드리는 곳이 여기다. 그래서 `auth.log`가 보안에서 중요하다.

## 알아둘 네 가지 기록

### 1. 비밀번호 실패

```
Failed password for urigg from 192.168.0.50 port 54321 ssh2
```

위 로그는 "`urigg` 계정으로 `192.168.0.50`에서 접속을 시도했는데 비밀번호가 틀렸다" 라는 뜻이다. `from` 뒤의 숫자가 어디서 접속을 시도했는지 알려주는 IP 주소이다. 공격자를 특정하는 출발점이 된다.

### 2. 없는 계정으로 시도

```
Failed password for invalid user admin from 203.0.113.9 port 40122 ssh2
```

`invalid user`가 붙었다. "아예 존재하지도 않는 계정으로 로그인을 시도했다" 라는 뜻이다. 이것이 중요한 이유는 **정상 사용자는 자기 계정 이름을 틀리지 않기 때문**이다. `invalid user`가 `admin`, `root`, `test`, `oracle` 같은 흔한 이름으로 줄줄이 나온다면, 그건 공격자가 계정 이름을 찍어보고 있다는 확실한 신호가 된다.

### 3. 로그인 성공

```
Accepted password for urigg from 192.168.0.10 port 55123 ssh2
```

이 줄은 "`urigg` 계정으로 `192.168.0.10`에서 접속에 성공했다"를 의미한다. 평소엔 반가운 줄이지만, 바로 앞에 실패 기록이 수백 줄 있었다면 매우 섬뜩한 한 줄이 될 것이다.

### 4. sudo 사용

```
urigg : TTY=pts/0 ; PWD=/home/urigg ; USER=root ; COMMAND=/usr/bin/apt update
```

`urigg`가 `/home/urigg` 위치에서, `root` 권한으로 `apt update`를 실행했다는 기록이다. 2편에서 배운 `sudo`가 쓰일 때마다 이렇게 기록에 남는다. 주목할 점은 어떤 명령을 실행했는지까지 남는다는 것이다. 공격자가 침입해서 `sudo`로 뭔가를 했다면, **그 명령이 그대로 여기 남는다.** 침입 후 무슨 짓을 했는지 추적하는 핵심 단서이다.

## 정리

- 로그는 프로그램이 **자동으로, 사건이 일어난 그 순간에** 남기는 기록이다. 텍스트 파일로 남는 CCTV와 같다.
- 침입은 한참 뒤에 발견되고, 공격은 흔적이 튀고, 공격자는 로그부터 지운다. 그래서 로그가 보안의 핵심 증거가 된다.
- 로그는 `/var/log`에 모여 있고, 보안에서 보는 것은 `auth.log`다. `.1`, `.2.gz`는 로그 로테이션의 결과다.
- `auth.log`는 `syslog` 주인에 `adm` 그룹으로 잠겨 있다. 민감한 정보가 담기기 때문이며, `adm` 그룹이면 `sudo` 없이 읽을 수 있다.
- 로그 한 줄은 **시각 / 호스트명 / 프로그램[PID] / 내용** 네 덩어리이고, 실제로는 **내용만** 읽으면 된다.
- `Failed password`, `invalid user`, `Accepted password`, `sudo` 네 가지만 알아도 대부분의 줄이 읽힌다.

이번 편에선 로그가 무엇이고, 어디에 쌓이며, 한 줄을 어떻게 읽는지까지 알아보았다. 그런데 실제 로그는 수천, 수만 줄이다. 그 안에서 실패 기록이 쌓인 구간을 눈으로 훑어 찾아내는 건 불가능하다. 다음 편에선 5편에서 배운 `grep`과 파이프(`|`)를 실제 로그에 직접 써서 침입 흔적을 찾아보고, 그 결과를 파일로 남기는 **리다이렉션**까지 다룬다.
